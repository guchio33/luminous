# ADR-0001: モノレポアーキテクチャの採用

## ステータス

承認済み

## コンテキスト

Luminous プロジェクトはフロントエンド（Next.js）とバックエンド（Hono）で構成される。
開発効率と保守性を高めるため、リポジトリ構成を決定する必要がある。

### 選択肢

1. **モノレポ（pnpm workspace）** - 単一リポジトリで全パッケージを管理
2. **マルチレポ** - FE/BE を別リポジトリで管理
3. **モノリス** - 単一パッケージで全てを管理

## 決定

**pnpm workspace によるモノレポ構成を採用する。**

```
luminous/
├── apps/
│   ├── web/          # @luminous/web (Next.js)
│   └── api/          # @luminous/api (Hono)
├── packages/
│   └── shared/       # @luminous/shared (共通型・ユーティリティ)
├── package.json      # ワークスペース管理
├── pnpm-workspace.yaml
└── tsconfig.base.json
```

## 理由

### 採用理由

1. **型の共有が容易**
   - `@luminous/shared` で API の型定義を FE/BE で共有
   - 型の不整合を防止

2. **依存関係の一元管理**
   - pnpm の厳格な依存解決による安全性
   - 共通 devDependencies の重複排除

3. **CI/CD の効率化**
   - 変更のあったパッケージのみビルド・テスト可能
   - 単一リポジトリで PR レビューが完結

4. **開発体験の向上**
   - `pnpm dev` で全アプリを一括起動
   - ホットリロードが全パッケージで有効

### 不採用理由

- **マルチレポ**: 型共有の複雑化、リリース同期の困難さ
- **モノリス**: 関心の分離が困難、スケールしにくい

## 影響

### ポジティブ

- FE/BE 間の型安全性が保証される
- 新規パッケージの追加が容易
- 統一されたリンター・フォーマッター設定

### ネガティブ

- 初期セットアップの複雑さ
- CI の設定が若干複雑
